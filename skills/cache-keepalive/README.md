# Cache keepalive

Claude Code の会話キャッシュを、アイドル中の短いリクエストで維持する実験用 Mod です。
同じセッションの `$.model.fork()` を使い、50 分おきに短い応答を求めます。
読み込むだけではリクエストを送りません。

キャッシュ保持や料金削減を保証するものではありません。
別セッションへの単なる Ping は、元の会話と同じキャッシュ prefix を読みません。

## 起動する

Claude Code 2.1.287 以降と、Mod の実行を許可したワークスペースが必要です。
このパッケージの検証対象は 2.1.289 です。

1. リポジトリを取得します。

   ```sh
   git clone https://github.com/yxhta/skills.git
   cd skills
   ```

2. コストと TTL の条件を確認してから、対象セッションだけに設定して起動します。

   ```sh
   CLAUDE_CODE_PROMPT_CACHE_TTL=1h \
   CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h \
   claude --plugin-dir "$PWD/skills/cache-keepalive/mod"
   ```

   この指定はホームディレクトリの設定ファイルを書き換えません。
   ただし、この Claude プロセス内のサブエージェントや補助リクエストにも
   1 時間 TTL が適用されます。キャッシュ書き込みの単価が上がる場合があります。
   既存の `FORCE_PROMPT_CACHING_5M=1` やキャッシュ無効化設定があれば、開始を拒否します。

3. 通常の会話を 1 ターン実行します。
   Mod が、キャッシュ利用のあるメインリクエストを観測する必要があります。
   短すぎるコンテキストではキャッシュ対象にならないことがあります。

4. Claude Code の入力欄で、必要な時間だけ開始します。

   ```text
   /cache-ping start 4
   /cache-ping status
   /cache-ping stop
   ```

   時間は 1〜8 の整数です。省略時は 4 時間、1 回の実行で最大 10 リクエストです。
   開始コマンドの再実行は、稼働中の期限やリクエスト予算を延長しません。

スキルの手順だけを導入する場合は、次のコマンドも使えます。
スキルは `/cache-keepalive`、Mod の操作は `/cache-ping` で呼び出します。
Mod のロードには、導入先の `cache-keepalive/mod` を別途 `--plugin-dir` に指定してください。

```sh
npx skills add yxhta/skills --skill cache-keepalive
```

## 50 分間隔にする理由

[公式ドキュメント](https://code.claude.com/docs/en/prompt-caching#cache-lifetime)では、
キャッシュヒットで TTL が更新されます。1 時間ちょうどの間隔では、通信遅延や
スリープ復帰で失効に間に合わないため、10 分の余裕を設けます。

メイン会話と fork は別の TTL 区分です。サブスクリプションのメイン会話が
1 時間でも、fork の既定値は通常 5 分です。この Mod は両方が明示的に
`1h` になっていなければ開始しません。5 分 TTL への自動切り替えは行いません。

設定と環境変数の読取結果から条件を判定します。
ゲートウェイやプロバイダーが、実際に指定 TTL を守るかまでは確認できません。

## 動作と停止条件

- 最後の成功したメインリクエスト、またはキャッシュヒットした Ping の開始時刻から 50 分後に実行します
- メイン会話の生成中には新しい Ping を開始しません
- Ping は同時に 1 件だけです。実行中に停止して再開しても、重複リクエストを作りません
- 成功した通常の会話で次回時刻が更新されるため、作業中の不要な Ping を減らします
- キャッシュ読み取りが 0 の Ping は、自動継続を停止します
- エラー時は待ち時間を延ばして再試行します。連続 3 回の失敗、最大リクエスト数、期限で停止します
- スリープなどでキャッシュ期限を過ぎた場合、古い会話を自動で再キャッシュしません
- `/clear`、`/resume`、`/branch`、終了で停止します。再開は手動です
- `/compact` 後は、新しいメインリクエストを観測するまで待ちます
- Mod の再ロード後は無効状態に戻ります。バックグラウンド常駐プロセスや永続スケジュールは作りません

状態表示には送信数と、fork が返したキャッシュ読み取り・書き込み・出力トークン数が出ます。
利用量を返さなかったエラーの消費量は不明です。送信済みリクエストが無料だったとは判断できません。
Ping の応答は元の会話へ追加しません。これらの数値は料金見積もりではありません。

## コストと制約

[公式 Mods API](https://code.claude.com/docs/en/plugins/mods/api#call-a-model) の
`$.model.fork()` は、同じモデルとシステムプロンプトのスナップショットを使います。
ツールを実行せず、元の会話へ回答を追加しません。
ユーザーの既存プランまたは API アカウントの利用量を消費します。

公開されている fork API には、出力トークン上限や中断用パラメーターがありません。
短い回答を求めても、出力の長さや 1 回あたりの料金は保証できません。
停止やタイムアウトは次の Ping を止めますが、送信済みのリクエストは完了する場合があります。
Ping 開始後に通常の会話を始めた場合も、進行中の Ping をキャンセルできません。

キャッシュは prefix の完全一致が前提です。モデル・effort・ツール構成の変更や
圧縮などで一部または全部が失効します。古いスナップショットのヒットだけでは、
次のメイン会話が全体を再利用できることの証明にはなりません。

実機の長時間キャッシュ保持と料金削減は未検証です。
[検証手順と確認済み範囲](verification.md)を参照してください。
